## 1. サービス概要

receipt-shopping-support（仮）は、消耗品の購入を「レシートを撮るだけ」で管理できるアプリです。レシートを撮影すると消費ペースを割り出して、「そろそろ切れる」タイミングをユーザーが把握できるようにします。

**誰の、どんな課題を、どう解決するか：** ストックを"記憶と勘"で管理し続けることに疲れた人が、自分で数えることも記録することもなく、必要なものを必要な分だけ計画的に買えるようにします。

---

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

**買い物の段取りが悪い自分自身の経験から**<br>
（買い物で消耗品を買うとき、前回「買った」ことは覚えていても「どの種類を買ったか」など細かいことを忘れがち）

例：<br>
月1〜2回ローテーションで購入しているサプリグミ3種（亜鉛・鉄・マルチビタミン）をストック数を把握せず当てずっぽうで買い、結果ストックがある亜鉛グミを二重買いし、鉄グミのストックを切らす。<br>
もちろん対策として全部買えばストックは切らさない。しかし、それだと収納スペースが溢れて物理的なストレスになるし、うまく買えなかったこと自体にもストレスを感じてしまう。

さらに私にとってより負担なのが、ストックの状態を頭の中で抱え続け「今日は何を買えばいいか」「アレはそろそろ切れるのでは」とふと考えてしまうことです。<br>
これらの考えが不意に湧くたびに、集中が切れてそのときやっている作業が止まってしまいます。この度重なる認知負荷が最も厄介と感じています。

### 2-2. なぜそれが「気になった」のか

**表向きの理由：**
- もったいない精神
- ケチで慎重な性格
- 過去に切らしたり買いすぎたりして怒られた経験

**本当の理由：**<br>
「必要なものを必要な分だけ、計画的で客観的な基準にもとづいて買うサイクル」を確立し、認知負荷を減らして楽になりたい

**気づき：**<br>
困っているのはお金の無駄遣いや実際にストックを切らすことではなく、買うべきかどうかの判断を頭の片隅に置き続けること

## 3. 課題の整理

### 3-1. 表に見えている困りごと

買うべきもののストック数を正確に把握できておらず、買い物のたびに家に「何が・あといくつあるか」が分からない。結果、持っている種類を二重に買い、別の種類を切らす。

### 3-2. 本当に解決したい課題は何か

**「なぜそれが困るのか？」**
- なぜ①：二重買いだと収納スペースが圧迫される一方で、本当に必要なものはストックが切れるから。「必要な分だけ」買えていない。
- なぜ②：「何が・あといくつあるか」を正確に覚えていられず、当てにならない記憶に頼っているから。かといって、メモやリマインダーなどに書き出して管理するのも苦手で続かない。
- なぜ③：ストック数を常に警戒し続けること自体が日頃の負担になるから。買い物前に収納スペースへ行ってストックを数えるのも時間と手間がかかる。

**→ 本当に解決したい課題：** 日用品のストックを自分の"記憶と勘"で管理し続けることによる、終わりがなく断続的に割り込んでくる認知負荷から解放されたい。

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

このアプリが最も必要になるのは、自分の消耗品を自分の裁量で管理しているが、その管理を記憶や勘に頼っていて破綻している人。具体的には、開発者自身をモデルにした次の1人。

**年齢設定**

- 年齢：20代後半・一人暮らしの社会人
- 理由：社会人になって実家を出て、自分の生活で必要な消耗品を選び・買い・切らさず回す責任を、初めて一通り自分ひとりで負うようになる年代だから。また、生活のパターン（よく買う消耗品の顔ぶれ）がある程度固まってくる年代でもある。買い物自体は全世代が行うが、「自分の消耗品ストックを自分の判断で管理する負担」が実感として立ち上がり、かつスマホ操作に抵抗がなくレシート撮影という手段も自然に受け入れられるであろうこの層を、最初のターゲットにする。

**生活・状況設定**

- 生活・状況：買い物の段取りが苦手。家に同じものが3個以上あることが多い一方で、収納スペースは溢れているのに肝心のものは切れている。「何が・あといくつあるか」を把握しないまま買い物に行っている。
- 理由：この「何が・あといくつあるか」を **把握できていない** 状態そのものが課題の中心。ストックの記録と消費ペースの推定をアプリ側に肩代わりさせることで、"記憶と勘"で管理し続ける負担から解放する。なお、一人暮らしを想定するため、消費ペースは「1人が使って減っていく」ことを前提に推定する（同居人と共有する世帯での利用は9章の発展案とする）。

**環境設定**

- 環境：スマホの基本操作はできる。ただし、メモやリマインダーで買い物の記録・管理を続けようとしても継続できず、これまで何度も挫折している。
- 理由：記録の継続を求める仕組みは、この人には必ず破綻する（3章のなぜ②）。だから「レシートを撮る」という認知負荷の極めて低い行為ひとつで完結させ、そもそも継続的な手入力・記録を一切させない設計にする。手段・手間を減らすことでハードルを下げる。

### 4-2. 自分とユーザーの距離

- 選択：**自分自身**
- 理由：開発者自身が日常的に困っている実体験から出発しているから。ストック数を記憶で管理しきれず二重買い・買い忘れを繰り返してきたのも、メモやリマインダーでの管理に挫折してきたのも、すべて自分自身の話なので「どんな仕組みなら自分が実際に使い続けられるか」を、想像ではなく実感で判断できる。そんな自分を想定ユーザーに据えて満足できるアプリが作れたら、同じようにストックで悩みを持つユーザーにも納得してもらえると信じている。

### 4-3. 実際に使われる可能性について（需要・存在確認）

- **最初に使ってくれそうな人は誰か：**<br>
開発者自身と同じ悩みを持つ人。以前開催されたアプリブレスト案LT発表で「レシートを撮るだけで記録が済むなら欲しい」という反応を複数得られており（挙手制のアンケートで15人が欲しいと回答）、「不要」という声はなかった。最低限の需要は確認できている。

- **その人はどんな場面でこのアプリを思い出すか：**<br>
買い物に行く前や、買い物中に「これ、家にまだあったっけ？」と迷ったとき。
- **今の生活の中で、代わりに使っているものは何か：**<br>
メモやリマインダーを利用するが、その実質は結局自分の"記憶と勘"。（4-1の環境設定と同じ）。

- **それを置き換えてまで使う理由はあるか：**<br>
既存手段（記憶・メモなど）はいずれも「覚えておく」「記録し続ける」という負担をユーザーに課す。本アプリは「レシートを撮る」一手だけで完結し、その負担そのものを消す。LT会でもこの"手間の省略"が最も強く支持された点だった。

- **LT会で得た学び**：<br>
ストック状況をどう把握したいか（切れるまでの残り日数か、最終購入日か、残り個数か）には人それぞれ好みがあると分かった。当初は「切れるまでの残り日数」＝「次に買うまでの期間」ひとつで十分と考えていたが、他の見せ方も求められた。この気づきは、どの情報をMVPに含めるかの判断（7章）に反映する。

### 4-4. ユーザーがサービスを導入して利用するまでのイメージ

- **どんな場面・困りごとがきっかけで思い出すか：**<br>
二重買いや買い忘れを実際にした直後や、「また無駄な買い方をした」と感じたとき。あるいは、買い物前に「何がどれだけあったか」を思い出せず迷ったとき。この"うまく買えなかった"実感が、アプリを求める入口になる。
- **最初の一歩（登録・導入）：**<br>
買い物をしたらスマホでWebアプリを開き、レシートを撮影する。初回では消費ペースはデフォルトのストックの周期日数で登録される。次回購入までの日数の目処が立っている場合は、任意に設定することもできる。2回目以降の購入では実際の購入間隔の日数に置き換わる（任意設定は引き続き可能）。
このように基本は撮影だけ、面倒な準備（周期日数入力など）は必須にしない設計にする。「使い始めるための作業」自体が継続の最初の障壁になるため、そこを限りなくゼロに近づける。<br>
**※データ保存のためアカウント登録は必要だが、登録自体は最小限にとどめる。**<br>
- **利用を続ける理由：**<br>
記録を頑張るのではなく、撮った結果がひとりでに積み上がっていく——この「頑張らないのに賢くなる」感覚が継続の理由になる。使うほど購入履歴が溜まり、消耗品ごとの消費ペースの推定精度が上がっていく。つまり「使い続けるほど、補充通知が自分の生活に馴染んで当たる」ようになる。ユーザーはレシートを撮るだけで、"切れる前に教えてくれる"状態が育っていく。

## 5. 既存サービス・競合調査

### 5-1. 似たサービスの調査

**うちフリッジ（レシートから簡単消費期限管理・食材管理）**

- URL：https://apps.apple.com/jp/app/id6760467570
- どんなことができるか：レシートを撮影して、食材の残り日数をリスト化して管理する。「レシートを撮影して完結」のコンセプトが同じで、特に食品を対象とした賞味期限や消費期限切れ防止を目的にしている。

**ストックスナップ（日用品の在庫管理＆リマインダー）**

- URL：https://play.google.com/store/apps/details?id=com.sokuma.stock_snap_app
- どんなことができるか：日用品をカメラで撮影して残量を管理し、通知で知らせる。対象は非食品の日用品で、買い忘れ防止・補充通知を目的にしている。レシート撮影ではなく、対象のものを記録用に撮影する点が異なる。

**3アプリ比較**

| | 対象 | 入力方法 | 消費の減り方をどう知る | 主目的 |
|---|---|---|---|---|
| うちフリッジ | 食品 | レシート撮影 | 消費/賞味期限（日付ベース） | フードロス防止 |
| ストックスナップ | 日用品 | 品目ごとに撮影 | アプリが残量管理（品目単位） | 買い忘れ防止・通知 |
| 本アプリ | 消耗品 | レシート撮影（1枚で複数品目） | 購入履歴から消費ペースを推定 | 補充判断の認知負荷ゼロ化 |

### 5-2. それでも自分が作りたい理由

**両サービスは、私の目指すアプリと方向性や対象などにズレがあると感じたから。**

**うちフリッジ（レシート撮影 × 食品 × 消費・賞味期限で管理）：**<br>
UI/UXは自分のアプリでも参考にしたい。ただ対象が食品に限られていて、日用品などの消耗品を扱えないのがもったいないと感じた。加えて、うちフリッジを含む食品系アプリは「賞味期限＝日付」でストックを管理する発想に立っている。しかし消耗品は"期限が来て切れる"のではなく"使い切るペースで減っていく"。この「消費ペースで減る」という性質は「賞味期限＝日付」では管理できない。これが設計思想上の一番大きなズレだと思った。

**ストックスナップ（品目撮影 × 日用品 × 期限は入力の手間あり）：**<br>
対象に消耗品が含まれる日用品を扱っているものの、写真を撮る目的が「商品を把握する」ことにある点が異なる。それ以外にもストック管理のための入力が必要。さらに「完了」ボタンがあることから、買い物のあとにも入力する手間が残ると感じた。「少し見やすくなったメモ」という印象で、自分がずっと続けられなかった"品目ごとに数えて入力する"手間（収納スペースへ行く→数える→入力する）を、このアプリもまだ残していると感じた。

### 5-3. 差別化を「体験価値」で表現する

**私のアプリの差別化ポイント：**<br>
このアプリは、【自分の消耗品を"記憶と勘"で管理してきて、メモもストック入力も続かなかった人】が【"そろそろ切れるかも"とストレスになる瞬間】を感じなくなるアプリ。<br>
買い物のたびにレシートを撮るだけで、何かを数えることも「使った」と報告することもなく、実際にストックが切れる前に通知を受け取れる。既存アプリが「品目ごとに撮る・数える・入力する」という能動的な手間をユーザーに残しているのに対し、本アプリはその手間そのものを消す。ユーザーがやることは、買い物という行為の一環に「レシートを撮る」工程を１つ足すだけ。使い続けるほど購入履歴が溜まり、"切れる前に教えてくれる"精度が上がっていく。

## 6. このサービスで提供したい価値

### 6-1. ユーザーの変化

- **行動の変化：** 買い物のたびに「何が・あといくつあるか」を思い出そうとする／店で迷う、という行動がなくなる。代わりに、レシートを撮るという一動作だけが習慣に加わる。買うべきものは、切れる前に届く通知によって判断できるようになる。
- **気持ちの変化：**「そろそろ切れるのでは」と作業中に割り込んできた不安や、二重買い・買い忘れをしたときの「うまく買えなかった」という苛立ちから解放される。ストックのことを頭の片隅に置かなくて済む。
- **考え方の変化：**「必要なものを、必要な分だけ」買うことが、記憶力や意志の問題ではなくなる。ストック管理を"頑張って続けるもの"にさせないことで、購入の判断を自分で抱え込まなくてよいと思えるようになる。

### 6-2. 価値を一文で表す

このサービスは、必要なものを必要な分だけ計画的に買いたいのに、記憶や勘頼りで破綻していた人が、客観的な基準で"いつ・何を買うか"を機械的に決められるようになるサービス。

## 7. このアプリで実現すること

### MVPで作る機能

差別化の核（「レシートを撮るだけ」でストック管理ができるか）に絞る。

- **ログイン／新規登録**：<br>
記録した情報を保存するためのユーザーアカウント。登録は最小限（メール＋パスワード程度）に留め、初期のストック入力のような重い準備は課さない。
- **レシート撮影 → 品目抽出（OCR）**：<br>
消耗品の品目を読み取る。「レシートを撮るだけ」の心臓部。外部API（Cloud Vision API）を利用する方針。
- **レシート読み取り結果の確認・登録画面**：<br>
OCRで読み取った品目の一覧を表示し、ユーザーが登録内容を確定する画面。ここで次の操作を行う。
  - 選別：読み取った品目のうち、ストックとして管理したいものを選ぶ（消耗品以外の品目も読み取られるため、登録対象はユーザーが選択する）。
  - 名寄せ：各品目を「既存のストックに紐付ける」か「新規のストックとして登録する」かを選ぶ。これにより、表記が揺れても同一の消耗品として購入履歴を積み上げられる。
  - 読み取りの確認・修正：OCRの誤読を、登録前にユーザーが確認・修正できる。

  ※これらはいずれもMVPではユーザーの手動操作とし、自動での候補提示や自動紐付けは本リリースで検討する。
- **消耗品のストック登録・管理**：<br>
抽出した品目をストックとして登録し、一覧で見られる。
- **消費ペースの推定（初期はデフォルト周期）**：<br>
品目ごとに「次に切れるのはいつか」を見積もる。初回はアプリ共通のデフォルト周期（例：30日）を置いて回り始め、ユーザーが任意で品目ごとの周期を設定することもできる。2回目以降の購入からは、実際の購入間隔で周期を補正していく。
- **最終購入日の表示**：レシートの日付から自動取得（ユーザー入力ゼロ）。<br>
※LT会で要望のあった表示（切れるまでの残り日数／最終購入日／現在の残り個数）のうち、OCRで自動取得できる最終購入日はMVPに含める。"どれを主に見せるか"の切り替え機能は本リリース（9章）に回す。
- **切れそうな品目のアプリ内表示**：アプリを開いたとき、推定にもとづき「そろそろ切れそう」な品目を表示する。<br>
※MVPでは"外から届く"通知は実装せず、この表示で消費ペース推定の当たり外れを検証する。

### 本リリースで作る機能

核が検証できてから足す。

- **Web Pushによる補充通知**：アプリを開いていなくても、切れる前にスマホへ届ける。"向こうから教えてくれる"体験の完成形。
- **ゲストログイン**（登録のハードルをさらに下げる）
- **OCRの精度向上・対応レシート拡大**
- **消費ペース推定ロジックの高度化**
- **「現在の残り個数」の手動編集**：「レシートを撮るだけ」の標準フローには置かず、任意編集として後付け
- **通知条件の細かな設定**

## 8. このアプリの懸念点とその対策

### 懸念点①：ユーザーがレシートを撮り続けてくれるか

- **何が問題になりそうか：**<br>
このアプリは、レシートを撮り続けて購入履歴が溜まってきたところで真価を発揮する。しかし「価値を感じる瞬間（切れそうと通知が来る）」は受け身で得られるのに対し、「作業が必要な瞬間（レシートを撮る）」は能動的に行う必要がある。この非対称のため、撮影を忘れる・面倒になってやめると、価値が育つ前に離脱する恐れがある。
- **なぜそう思うか：**<br>
想定ユーザー（4章）は、そもそもメモやリマインダーでの記録が続かなかった人だから。「記録の継続」を求める仕組みは、この人には破綻しやすい。
- **考えている対策：**<br>
ユーザーに課す手間を、既存手段より構造的に小さくする。メモ方式は「①収納スペースへ行く→②数える→③品目ごとに入力（複数回）」という最低3ステップを要求するのに対し、本アプリは「買ったときにレシートを1枚撮る」の基本1ステップで済む。しかも新しい習慣をゼロから作らせるのではなく、"買い物のたびに必ず手に入るレシート"という既存の行為に相乗りする。継続を「意志」ではなく「手間の少なさ」と「既存行動への便乗」で支える設計にする。

### 懸念点②：消費ペースの推定が当たるか

- **何が問題になりそうか：**<br>
「切れる前に通知する」ためには、品目ごとに「いつ使い切るか」を予測する必要がある。しかし、消費ペースは人・時期・品目でばらつき、購入履歴だけから正確に当てるのは難しい。外れれば「まだあるのに通知が来る／切れてから通知が来る」となり、アプリの信頼が崩れる。
- **なぜそう思うか：**<br>
差別化の核（5-3・6-2）が、この推定の精度にかかっているから。しかも購入履歴が浅いうち（使い始め）はデータが少なく、最も外れやすい。
- **考えている対策：**<br>
初期は精度を欲張らず、シンプルなルールから始める。初回はデフォルトあるいはユーザーが任意で決めた周期日数で、2回目以降の購入で実際の購入間隔に置き換えて補正していく。そのため、デフォルト周期のままの品目や購入履歴が浅いうちは推定が外れやすいが、これは想定内であり「完璧な予測」ではなく「記憶と勘よりマシ」を最初のゴールに置く。なお、MVPでは通知機能を実装しないため、この推定の当たり外れは「アプリを開いたときに表示される"切れそうな品目"が、実際の消費と合っているか」をユーザー自身に確認してもらう形で検証する。通知という"届け方"の妥当性は、推定精度が確かめられた後、本リリースのWeb Push実装とあわせて検証する。精度の高度化も本リリースに回し、MVPでは"予測が当たるかを確かめること自体"を目的にする。

### 懸念点③：OCRがレシートを正しく読めるか

- **何が問題になりそうか：**<br>
レシートは店舗ごとにフォーマットがバラバラで、略称表記（例：「ﾄｲﾚｯﾄP」）や感熱紙のかすれもある。品目を安定して正しく抽出できないと、"撮るだけ"の体験が崩れる。
- **なぜそう思うか：**<br>
レシートOCRは一般に難度が高く、MVPの中で最も実装リスクが高い部分だから。
- **考えている対策：**<br>
自前実装せず、実績のある外部OCR APIを利用して精度リスクを外部に寄せる（7章）。それでも誤読は残るため、読み取り結果をユーザーが確認・修正できる余地を残す。<br>
なお、この「確認・修正の余地」は、懸念①で掲げた「手間を最小化して継続させる」という方針とトレードオフの関係にあり、確認の手間が増えるほど"撮るだけ"の体験は損なわれ、継続が危うくなる。しかし、本アプリは現時点では、ストックデータの信頼性を損なう誤読を放置するより、確認の一手間を許容して正確さを優先する方針を採る。ただし、その一手間をどこまで許容できるか（どの程度の誤読率なら確認をスキップできるかなど）はMVPの検証で見極めるべき点であり、実装方針とあわせて講師に相談して詰める。

### 懸念点④：レシートから、どの品目をストックとして登録するか（選別）

- 何が問題になりそうか：<br>
レシート1枚には、管理したい消耗品だけでなく、その日たまたま買った食品や一度きりの買い物など、ストックとして追いかける必要のない品目も混ざる。読み取った品目をすべて自動でストック登録すると、一覧が不要な品目で埋まり、「何が切れそうか」が見えにくくなる。
- なぜそう思うか：<br>
本アプリが管理したい「消耗品」の中心は日用品だが、ユーザーによっては賞味期限の長い食品（グラノーラなど）を消費ペースで管理したい場合もある。つまり「登録すべき品目」は一律に線引きできず、人によって異なる。
- 考えている対策：<br>
どの品目を登録するかを機械的に判定せず、ユーザーに委ねる。読み取り結果の確認・登録画面で、読み取った品目をすべて選択可能にし、その中からユーザーが管理したいものだけを選んで登録する。食品か日用品かでアプリ側が制限を設けることはしない。

### 懸念点⑤：表記が揺れる品目を、同一の消耗品としてどう紐付けるか（名寄せ）

- 何が問題になりそうか：<br>
消費ペースの推定は「前回買った品目と今回買った品目が同じものだ」と分かることが前提になる。しかしレシートの品名は店ごとに表記が揺れる（例：「ﾄｲﾚｯﾄP」「トイレットペーパー12R」）ため、OCRで文字を正しく読み取れても、それを同一の消耗品として結びつける「名寄せ」は別の課題として残る。紐付けができないと、同じ消耗品が毎回別物として登録され、購入間隔が取れず、推定そのものが成り立たない。
- なぜそう思うか：<br>
名寄せはOCRの読み取り精度（懸念③）とは別のレイヤーの問題であり、文字が正しく読めても自動では解決しない。そして消費ペース推定（MVPの核）の前提条件にあたるため、ここが崩れるとMVPで検証したいこと自体が検証できなくなる。
- 考えている対策：<br>
MVPでは自動の名寄せは行わず、ユーザーの手動確認で成立させる。読み取り結果の確認・登録画面で、各品目を「既存のストックに紐付ける」か「新規のストックとして登録する」かユーザーが選ぶ。これにより、表記が揺れても購入履歴を同一の消耗品として積み上げられる。表記の類似から自動で紐付け候補を提示する仕組みは、本リリースで検討する。

## 9. 今後の展開・発展の方向性

### 観点

- **データが溜まると何ができる？**：購入履歴が溜まるほど、品目ごとの消費ペース推定が正確になり、通知が生活に馴染んで当たるようになる（6章の「使い続けるほど賢くなる」の延長）。さらに蓄積が進めば、「この人はこの消耗品を平均○週間で使い切る」という個人ごとの消費パターンが見えてくる。
- **ユーザーはなぜ使い続ける？**：ユーザーが新しい操作を覚えるのではなく、「買い物→レシート撮影」という既存行為に価値を積み上げる設計により続けやすさを提供する。

### 今考えている発展案

**機能追加の方向性**

- **通販サイトとの連携**：LT会で出た要望。ネット通販でまとめ買いする場面では紙のレシートが出ない。通販の購入履歴と連携できれば、店頭・ネット両方の購入を取りこぼさずストックに反映できる。
- **店舗情報の活用**：OCRで店舗情報も読み取り、どの店でよく買うかを記録し、補充のサイクルを立てる手がかりにする（よく買う店を把握していれば、次にどこで補充するかを計画しやすくなる）。
- **「現在の残り個数」の手動編集**：LT会で出たストック把握のための要望。「レシートを撮るだけ」の標準フローには置かないが、正確にストック数まで管理したいユーザー向けの任意編集とする。
- **消費ペース推定ロジックの高度化**：初期のシンプルなルール（購入履歴の間隔）から、品目ごと・季節ごとの消費特性を学習する方向へ育てるなど。
- **家族・同居人との共有**：世帯単位でストックを共有し、誰かが買えば全員のストックに反映される（1人での管理から1世帯での管理への拡張）。

**UI・体験の改善**

- **ストック状況の見せ方を選べるようにする**：LT会で「切れるまでの残り日数／最終購入日／残り個数」など人によって見たい情報が違うと判明したため。MVPでは自動取得できる最終購入日の表示にとどめ、複数の見せ方から選べる切り替えは本リリースで対応する。

## 10. 技術スタック

### 10-1. 使用予定の技術

- フレームワーク：Ruby on Rails
- DB：PostgreSQL（本番のホスティングは Neon）
- デプロイ先（インフラ）：Render
- OCR：Cloud Vision API（外部API）
- 通知（本リリース）：Web Push （※通知はMVPには含めず、本リリースで実装）

### 10-2. 技術選定の比較検討

| 分類 | 候補 | 採用/不採用 | 理由 |
|---|---|---|---|
| バックエンド | Ruby on Rails | 採用 | 学習の主軸で最も手が動く。卒業制作は新規学習コストを抑え、検証したい体験の実装に時間を使うため。 |
| フロントエンド | Hotwire（Turbo / Stimulus） | 採用 | Railsに標準同梱で追加学習が少なく、MVPに必要な動的UIを低コストで実現できる。本格的なSPA（React）は本リリース以降に回す。 |
| | React/Next.js | 不採用（将来検討） | 学習コスト・見積りの不確実性が高い。本リリース後にキャッチアップして組み込み判断（10-3参照）。 |
| OCR | Cloud Vision API | 採用 | Railsでの実装を扱った技術記事が複数あり、詰まったときに参照先がある（講師相談で確認）。 |
| | Tesseract（自前OCRエンジン） | 不採用 | 外部APIに頼らず自前運用する構成になり、精度確保・保守の負担が卒業制作には重い。 |
| DB | PostgreSQL | 採用 | Rails定番でRenderと同じ提供元、情報が豊富。先輩の卒業制作でも採用例が多い。 |
| | MySQL / SQLite | 不採用 | 選ぶ積極的理由がなく、PostgreSQLで情報・事例が揃うため。 |
| DB本番環境 | Neon（外部無料Postgres） | 採用 | Render内Postgresは無料が90日限定で以降有料。本番は無料枠を維持できるNeonに逃がす。先輩READMEでも同構成が多い。 |
| デプロイ（インフラ） | Render | 採用 | これまでのデプロイで利用経験あり。Rails記事が豊富。 |
| | Railway / Fly.io / Heroku | 不採用 | 恒久無料枠がない・トライアルのみ・有料前提で、学習検証用に不利。慣れているRenderを外す理由がない。 |
| 通知（本リリース） | Web Push | 採用 | アプリを開かなくても"向こうから届く"ため、コンセプト（頭で見張らなくてよい）に最も忠実。 |
| | メール通知 | 不採用 | 実装は堅いが即時性・気づきやすさで劣る。MVPで通知自体を外したため、本リリースは理想形のPushを選ぶ。 |
| | アプリ内通知のみ | MVPで採用 | 実装が軽く、MVPでの推定精度検証には十分。ただし"向こうから届く"体験は満たさないためMVP限定。 |
| 認証 | Devise | 採用 | セキュアな会員登録・ログイン・ログアウトを実現。 |

- 今回チャレンジしたい点：レシートOCR（外部API連携）と、購入履歴からの消費ペース推定ロジック。
- 不安な点：OCRの読み取り精度（8章③）と、消費ペース推定の妥当性（8章②）。

### 10-3. キャッチアップ不足の懸念

本アプリでは、OCR（外部API連携）と消費ペース推定という、これまでの学習範囲を越える実装に挑戦する。これらはキャッチアップに一定の時間を要し、Issueの見積りも読みにくいため、MVPでは機能を絞り、難度の高い要素（Web Push通知、推定ロジックの高度化）は本リリースに回す。<br>
※ Web Push通知は単にサーバーからJavaScriptを実行する機能ではなく、ブラウザの許可、Service Worker、Push購読情報、送信サーバー、OSごとの制約が関係する機能であり、iOSではPWA（プログレッシブ・ウェブ・アプリ）としてホーム画面に置く必要がある。本リリースの実装前に、対応バージョンや必要な設定を確認したうえで着手する。

特にReact/Next.jsについては、MVPでは採用せず必要最低限の技術スタック（Rails中心）で構築する。本リリース後にReact単体のキャッチアップと組み込みの技術検証を行ったうえで、組み込むかどうかを判断する方針とする。MVPの完成を最優先し、学習コストの高い技術は段階的に導入する。
